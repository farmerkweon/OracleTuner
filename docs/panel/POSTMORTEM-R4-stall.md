같은 시각에 스폰된 다른 4개 레인(R1/R2/R3/R5)은 모두 4~5분 내 완료했다. R4 만 정지했다.

## 원인 (규명)

**레인 범위가 과도했다.** R4 에 배정한 담당 파일 총량과 질문 수가 다른 레인의 2배 이상이었다:

| 레인 | 담당 총량 | 질문 수 | 결과 |
|---|---|---|---|
| R1 서버 | ~130 KB (11파일) | 5 | 4분 완료 |
| R2 웹코어 | ~110 KB (9파일) | 5 | 5분 완료 |
| R3 뷰 | ~180 KB (9파일) | 6 | 4분 완료 |
| R5 패키징 | ~70 KB + bat | 6 | 5분 완료 |
| **R4 Java** | **~155 KB (8파일) 중 단일 파일이 45 KB** | **6** | **정지** |

R3 가 총량은 더 컸는데도 완료한 점을 보면 총 바이트가 아니라 **단일 초대형 파일(`Exec.java` 45KB)에
대해 6개 질문이 전부 교차 참조를 요구한 것**이 문제였다고 본다. 행 제한·토너먼트·실행계획·Caps 가
모두 `Exec.java`/`Plan.java` 안에서 얽혀 있어, 좁게 grep 해도 반복 재방문이 누적됐을 가능성이 크다.
(정확한 내부 상태는 확인 불가 — 로그를 1행만 남기고 멈췄기 때문이다. 이것이 heartbeat 규약의 존재 이유다.)

## 교훈 → 규약 보강

1. **한 레인의 담당은 "단일 파일 30KB 초과가 1개 이하" 가 되도록 쪼갠다.**
   초대형 파일이 있으면 그 파일 하나만 보는 전용 레인을 만든다.
2. **한 레인의 질문은 4개 이하.** 질문이 서로 다른 파일을 교차 참조하면 더 줄인다.
3. **heartbeat 미준수 = 진단 불가.** 에이전트 프롬프트에 heartbeat 요구를 더 강하게 못박는다
   (이후 슬라이스 프롬프트에 이 사례를 명시해 반영했다).

## 재설계 — R4 를 대체한 것

R4 가 답해야 했던 질문 중 **가장 급한 것(행 인출 제한 + 메모리 판정)** 은
총괄이 직접 좁은 grep 3회 + 부분 Read 2회로 해결했다 (`FIX-SPEC-slice-C-rowlimit.md` 참조).
Java 를 대신 읽을 에이전트를 다시 띄우지 않고 **총괄이 직접 처리한 것이 결과적으로 더 빨랐다.**
